# How to add a frontend remote

Use when adding a new screen/feature to this repo's `web/` (`fulfillment-mfe`)
Module Federation remote, or when standing up a NEW remote for a bounded
context that doesn't have one yet. This is the Vite/React micro-frontend
layer that `warehouse-console` (the shell) lazy-loads at `/fulfillment/*`
— see that repo's `.claude/rules/frontend-mfe.md` for the shell-side half
of this contract.

## `vite.config.ts` must stay in OBJECT form, always

This repo's own `web/vite.config.ts` is the reference:

```ts
const IS_BUILD = process.argv.includes("build");
const PUBLIC_BASE = IS_BUILD ? "/mfes/fulfillment-execution/" : "/";

export default defineConfig({
  base: PUBLIC_BASE,
  plugins: [react(), federation({ name: "fulfillment_mfe", filename: "remoteEntry.js", exposes: { "./App": "./src/App.tsx" }, ... })],
  // ...
});
```

Never convert this to the callback form
(`defineConfig(({ command }) => ({...}))`) to compute `base` dynamically.
`web/vitest.config.ts` does `mergeConfig(viteConfig, defineConfig({...}))`,
and Vite throws `Error: Cannot merge config in form of callback` on a
function export — killing the ENTIRE test suite for a one-line config
change, not just the new test. This repo's own config file comment spells
out exactly this reasoning; read it before touching `base`.

## A tiny, relative `dist/remoteEntry.js` after build is CORRECT

After `npm run build` with the `/mfes/fulfillment-execution/` base,
`dist/remoteEntry.js` is a small relative re-export — grepping it for
`/mfes/fulfillment-execution/` returns zero matches. That is expected,
not a bug: `dist/index.html` carries the absolute prefixed URLs, every JS
chunk uses relative ESM imports, and the module-preload helper resolves
via `new URL("../" + e, import.meta.url)`, which is origin-relative to
wherever `remoteEntry.js` was actually fetched from — exactly what a
path-mounted remote needs. Verify correctness by serving the built image
and fetching through the real gateway path
(`http://localhost/mfes/fulfillment-execution/`), never by grepping the
built file for the expected prefix.

## `@warehouse/ui-kit` is a sibling checkout, not a registry package

`web/package.json` depends on it via `"file:../../warehouse-ui-kit"`. Any
domain-status color, chart, or shared layout primitive belongs in that
repo, not hand-rolled here — a remote reinventing its own palette instead
of consuming the shared UI kit is a bug, not a style choice (visual
consistency across the MFE boundary is the #1 place MFE UX fails).

## The remote already has a working `test` script — keep it that way

`web/package.json`'s `"test": "vitest run"` script is already correctly
wired (this remote is NOT one of the fleet's historically-missing-test-
script remotes). Confirm this repo's CI `web:` job
(`.github/workflows/ci.yml`) actually invokes `npm test`, not just
`npm run build`, before assuming a new `.test.ts` file you add will
actually run in CI — the job currently does: `npm ci`, `npm run lint`,
`npx tsc -b`, `npm test`, `npm run build`, against a dual checkout of
this repo plus `IQVO/warehouse-ui-kit@develop`.

## The Docker build recipe (packaging as a deployable nginx workload)

See this repo's own `web/Dockerfile` for the complete, working, heavily
commented recipe — copy it rather than re-deriving these traps from
scratch for a change to the build:

1. **Base image must be `node:22-bookworm-slim`, not an alpine or newer
   node image.** `web/package-lock.json` was generated by npm 10 and
   carries no Linux entries for Vite's platform-specific optional
   dependencies (`@rolldown/binding-linux-*`, `lightningcss-linux-*`).
   npm 11 rejects that lockfile outright with `EUSAGE "lock file out of
   sync"`; glibc (not musl) is what matches the published `*-gnu`
   bindings.
2. **Do NOT install from the committed lockfile, and do NOT reuse a host
   `node_modules`.** Both leave the native binding missing
   (`Cannot find native binding ... @rolldown/binding-linux-*`, a known
   npm/cli optional-dependency bug). The working recipe: `rm -rf
   node_modules package-lock.json` in the ui-kit build stage (it arrives
   as a named BuildKit context from a developer checkout), `COPY
   package.json ./` only, then `npm install --no-save`.
3. **`@warehouse/ui-kit` must be supplied as a named BuildKit context**,
   since it's a sibling checkout, not a registry dependency:
   ```bash
   docker build --build-context uikit=../../warehouse-ui-kit \
     -t warehouse/fulfillment-execution-frontend:local .
   ```

## Wiring into `warehouse-infra`'s deploy

A new remote isn't deployed automatically — `warehouse-infra`'s
`local.services` map and this repo's own Helm chart
(`charts/fulfillment-execution/`, `frontend.enabled` value, default
`false`) both need updating. See `warehouse-infra`'s AGENTS.md for the
Terraform side of this; this repo only needs to ship a working chart with
`frontend.enabled` wired to a toggle.

## Key commands

```bash
cd web
npm ci
npm run lint        # oxlint
npx tsc -b           # typecheck
npm test             # vitest run — confirm this actually runs your new test
npm run build        # tsc -b && vite build -> dist/
```

CI's `web:` job runs this exact sequence against a dual checkout (this
repo + `IQVO/warehouse-ui-kit@develop`) — reproduce that locally by
checking out `warehouse-ui-kit` as a real sibling directory if `npm ci`
behaves differently than CI. Note the `web:` job is entirely separate
from the Go module's quality gate (`make check`/`check-all`) — this
repo's `AGENTS.md` calls out `web/` as "entirely separate build, not part
of the Go module or its quality gate."
