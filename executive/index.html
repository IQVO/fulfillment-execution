why it exists

Picking drives throughput, so no unit of work may get lost

Turns released work into completed physical operations and makes it impossible to lose a unit of work. Upstream wes-work-planning decides a unit of work should happen now (WorkReleased event); this service turns it into a Task, lets a station pull it via claimNext with capability matching and earliest-CPT selection, and closes the loop by publishing TaskCompleted back…

Today

Work planning releases jobs; stations pull the most urgent one they are certified for, and unconfirmed claims flow back to the pool.

The catch

Every endpoint is open by design, the equipment (WCS) edge is not wired, and live hazard and layout checks still default to permissive.

what it does

Six capabilities carry a job from release to a labeled package

Pull-based dispatch

Stations ask for work and get the most urgent job they are certified to do.

Leased claims

A claim expires back to the pool if nobody confirms it, so work is never stranded.

Pack and label check

Packages are sealed from scanned items, then weighed: labeled if right, diverted if not.

Handling flags

Fragile, hazmat and gift-wrap needs travel with the job all the way to the package.

Process-path catalogue

A declared catalogue decides each job's type and skills; an unknown path is refused.

Throughput and agent tools

Throughput and on-time reports, plus agent tools to spot stuck tasks and triage backlog.

Pull-based task dispatch: claimNext(stationId, capabilities) selects the earliest-CPT pending task the station is certified for - the system never names a station in advance Leased, at-most-once claiming: a claim is time-boxed, renewable, and expiry returns the task to the pool (no stranded work) Pack and SLAM execution: seal a package from scanned contents, SLAM weigh-check applies a label within tolerance or diverts Handling flags: fragile, hazmat (a requiredCapability) and gift-wrap threading from release to package Process-path catalogue resolution: path_id mapped to task type and required capabilities from a declared YAML catalogue (unknown path is a hard error) Analytics and agent surface: throughput and on-time-to-CPT reports; MCP tools for queue status, stuck-task diagnosis and backlog triage

what could go wrong · and what we do about it

Our biggest risk is that anyone inside the cluster can call it

All REST and MCP endpoints are unauthenticated

All REST and MCP endpoints are unauthenticated (fleet identity layer removed by ADR-0022); relies on cluster-internal reachability

→

Reachable only inside the cluster today; the identity layer was removed fleet-wide on purpose

A bad process-path catalogue stops startup

Process-path catalogue is a fatal boot dependency: a missing or invalid PATH_CATALOGUE_FILE prevents startup

→

Failing fast is deliberate: an unknown path is a hard error, and helm-lint runs in CI

Duplicate protection needs Postgres to survive restarts

At-least-once Kafka consumption requires the processed_events dedup table; without Postgres the in-memory set resets on restart

→

Run with Postgres so the processed_events table makes double delivery harmless

The package code lives under an awkward name

Package aggregate lives in a Go package named pack (reserved keyword) - a persistent naming friction noted in the README

→

Called out in the README so newcomers are not surprised
