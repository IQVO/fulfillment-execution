Fulfillment Execution is the task-lifecycle core bounded context for Pick, Pack, and SLAM (Scan, Label, Apply, Manifest). It is downstream of Work Planning, which releases work into this service (over Kafka, not HTTP — see the repo README's Integration section), and this service in turn issues commands to WCS/equipment as physical work is executed.

The defining design rule is **pull, not push**: a station calls `claimNext(stationId, capabilities)` and the system selects the highest-priority (earliest CPT — Committed Processing Time) pending task the station is certified/equipped for. The system never names a station in advance. Assignment is **at-most-once**, enforced by a time-boxed **lease**: if a claim is not confirmed (renewed) or completed before the lease expires, the task automatically returns to the pool rather than vanishing.

This API's aggregates: **Task** (Pick | Pack | SLAM; Pending -&gt; Claimed(leased) -&gt; Completed), **Station** (a work position with a capability set, one occupant at a time), and **Package** (Pack path output — an order becomes a sealed carton; the SLAM weigh-check applies a shipping label or diverts the package on a weight discrepancy beyond tolerance). **OrderConsolidation** (Rebin fan-in) gates the pick -&gt; pack handoff: an order's PACK task is created only once every required line has arrived at Rebin (`POST /rebin/arrivals`).

**Out of scope / boundary**: this service does not plan or release work (that's Work Planning's job — it publishes `WorkReleased`, consumed here over Kafka), does not manage inventory reservations (that's Inventory Storage), and does not drive physical WCS/equipment directly over this API (that's a separate command channel). This API is HATEOAS-free by design (Richardson Maturity Level 2 is the target, not Level 3) — clients are expected to know the URL structure, not discover it via response links.
